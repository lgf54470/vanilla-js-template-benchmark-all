# ADR 0003: 引入工作空间作为全局数据隔离边界

- 状态：已采纳
- 日期：2026-08-27
- 相关模块/文档：`ARCHITECTURE.md §7`、`docs/Workspace.md`、`docs/Database.md`

## 背景

项目是单一使用者的自托管应用（`x-auth-password`
单密码鉴权，非多用户体系），但用户希望在不同生活情境（工作/学习/生活/娱乐/旅游等）下维护互不干扰的数据集，类比
shadcn 示例里的 Team Switcher，但语义上不是"团队协作"而是"个人多情境隔离"。

## 考虑过的选项

1. **不做隔离，所有模块数据全局共享**：实现最简单，但无法满足"不同情境数据互不干扰"的核心诉求。
2. **每个模块自行决定是否支持分类/标签**：灵活但不统一，每个模块要重新发明一套"分类"机制，且无法保证跨模块的一致体验（如统一的顶部切换器）。
3. **工作空间作为核心基础设施概念，所有业务表强制携带
   `workspace_id`**：统一的隔离边界，统一的切换 UI（侧栏顶部
   WorkspaceSwitcher），新模块无需额外设计就自动获得隔离能力。

## 决定

引入 `core_workspaces` 作为核心基础设施表，**所有 `[module]_xxx` 业务表强制携带
`workspace_id` 列**，通过 `createScopedRepository(...).forWorkspace(id)`
封装器在结构上保证业务代码无法绕过该过滤条件；前端 Sidebar 顶部的 Team Switcher
概念相应重构为 Workspace Switcher，种子 6
个系统工作空间（默认/工作/学习/生活/娱乐/旅游）。

## 后果

- 每个新模块的表设计多一个必填列与一个复合索引，属于可接受的固定成本。
- 需要额外设计"切换工作空间时如何刷新已挂载模块"的约定（采用"整模块
  unmount/remount"而非要求每个模块自行实现响应式刷新，见
  `docs/Workspace.md §4`），降低了模块实现的复杂度但牺牲了切换时的一点点状态保留能力（如切换前正在编辑的表单会丢失，需配合前端草稿保存机制缓解，属于后续可优化项）。
- 删除自定义工作空间需要级联清理各模块数据，依赖模块通过能力注册表主动注册清理函数，存在"模块忘记注册"的风险，需靠
  code review 与文档提醒（`docs/Workspace.md §7`）弥补。
